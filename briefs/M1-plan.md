# M1 Implementation Plan — Manual reader

**From:** Opus 5 design agent · **To:** Fable / Sonnet 5 swarm · **Date:** 2026-08-06
**Companion:** `briefs/M1-manifest.json` (6 tasks, 4 waves)
**Builds on:** `briefs/M0-plan.md` — M0's toolchain, pins, build scripts and boot contract
are **fixed**. M1 adds one cabal library, one extra executable, and content.

---

## 1. Decision summary

| Question | Decision |
|---|---|
| How content reaches the app | `translations/*.md` are **embedded at compile time by Template Haskell** (`addDependentFile` + `lift`), then parsed **in Haskell, lazily, at runtime** |
| Where the parser lives | A new **miso-free `library` stanza in `site/sxc1-trainer.cabal`** (sources in `site/src/`; cabal target `lib:sxc1-trainer`, depended on by name as `sxc1-trainer`), using only boot libraries (`base`, `text`, `containers`, `bytestring`, `template-haskell`) |
| How the parser is tested | A second executable **`exe:content-check`** — a wasm32-wasi **command** module run on the host by `~/.ghc-wasm/wasm-run/bin/wasm-run.mjs`. Real Haskell unit + corpus tests, no browser, no native GHC, 0.11 s |
| Content unit | **The page.** A document is an ordered list of pages; a page is a list of blocks. `<!-- page N -->` markers become `id="page-N"` anchors and route captures — M2's citation target |
| Navigation | Two-level outline derived from the documents themselves: *groups* (guide book: front matter, the five PARTs, appendix) → *sections* → *subsections* |
| Routing | **Hash routing**, hand-written pure `parseRoute`/`renderRoute` over `Data.Text`; `windowSub "hashchange"` for change notification; plain `<a href="#/...">` for every link |
| JA page images | **Committed WebP** at `site/static/pages/<slug>/page-NN.webp` (~10.4 MB for all 108 pages, down from 34 MB of PNG), regenerated by a new `scripts/render-page-images.sh`. No build-time or CI-time image tooling |
| Build script changes | None needed for the app. `build-site.sh` gains one line in wave 3 so `check-site.sh` can run the content checker without building |

Everything below was **verified by compiling and running throwaway probes** against the
installed toolchain and the real translation corpus (see §2). No step of this plan is
speculative.

## 2. Probe results — verified facts (2026-08-06)

All probes were built in `/tmp/.../scratchpad`, never in the repo.

**P1 — Template Haskell can read the translations.** A `Q Exp` splice using
`runIO (decodeUtf8 <$> BS.readFile p)` + `lift` compiles under the wasm cross-compiler.
The external interpreter inherits GHC's cwd (the cabal *package* directory, i.e. `site/`)
and its WASI preopens are **not** restricted, so `../translations/guide-book.md` resolves.
All four documents embed; the resulting Core is a single `unpackCStringLen#` UTF-8 literal.

**P2 — `addDependentFile` alone is NOT enough.** Editing a translation and re-running
`wasm32-wasi-cabal build` did **nothing**: cabal decided the package was up to date and
never invoked GHC, so GHC's recompilation check never ran. Adding the file to
`extra-source-files:` fixes it — cabal then re-invokes GHC and GHC reports
`[../translations/guide-book.md changed]` and recompiles. **`extra-source-files:
../translations/*.md` is load-bearing for constraint 1 of the brief** ("a translation edit
must flow to the site by rebuilding"). Cabal prints one `[relative-path-outside]` warning
per component configure; that warning is about `cabal sdist`, which this project never
runs, and is documented in the README rather than worked around.

**P3 — `Lift Text` needs an explicit instance import.** Without `import Data.Text ()`
in the embedding module the build fails with
`No instance for (GHC.Internal.TH.Lift.Lift Data.Text.Internal.Text)`. Importing
`Data.Text.Encoding` is not enough.

**P4 — `foreign import javascript` returning `GHC.Wasm.Prim.JSString` does not link.**
It makes GHC emit a C stub referencing `HsJSString` / `rts_mkJSString`, which
`wasm32-wasi-clang` rejects. **Use Miso's own DSL instead** — this links and works:

```haskell
currentHash :: IO T.Text
currentHash = do
  loc <- jsg ("window" :: MisoString) ! ("location" :: MisoString)
  h   <- fromJSValUnchecked =<< loc ! ("hash" :: MisoString)
  pure (fromMisoString (h :: MisoString))
```

`jsg`, `(!)`, `fromJSValUnchecked`, `windowSub`, `emptyDecoder`, `intProp`, `MisoString`
and `fromMisoString` are **all re-exported by `import Miso`** (GHC reported the explicit
imports as redundant), so the app needs no extra import lines.

**P5 — the whole architecture boots in a real browser.** The probe app (library + TH
corpus + hash router + Miso view) was built, post-linked, served, and driven with headless
Chrome:

* `/` → `<p id="route">RHome</p>`
* `/#/m/guide-book/p/17/ja` → `<p id="route">RPage "guide-book" 17 True</p>`
* `<p>[71,15,6,16]</p>` — page counts of all four **real** translations, computed inside
  the browser from the TH-embedded text
* `<ol start="3">`, `<table>`, `<img loading="lazy" src="pages/guide-book/page-17.webp">`
  all render; `#boot-status` is `hidden`.

**P6 — sizes.** `app.wasm` grew from M0's **2 856 541 B raw / 644 452 B gzip** to
**3 171 617 B raw / 723 724 B gzip** with all four documents and the router embedded:
**+79 KB gzipped for the entire corpus.** The `content-check` command module is 2.0 MB and
runs in **0.109 s**.

**P7 — `wasm-run.mjs` preopens `/`** (`preopens: { "/": "/" }`) and passes the real cwd,
so a wasm32-wasi command executable is a first-class host-side test runner. `wasmtime`
47.0.2 is also installed (`wasmtime run --dir=/ …`) as a backup runner.

**P8 — GHC 9.14 stage restriction.** A TH function cannot be spliced in the module that
defines it (`Level error: 'x' is used at level -1 but it is bound at level 0`). The embed
helper and the corpus module must be separate modules.

**P9 — compile-error noise.** Any type error in the module holding the splices makes GHC
print the *entire* 111 KB literal in the error message. Implementers should expect this and
scroll to the first `error:` line.

## 3. The corpus, as it actually is

Measured from `translations/*.md`, not assumed. These numbers are the golden values the
verification harness compares against.

| | guide-book | startup-guide | midi | oss |
|---|---:|---:|---:|---:|
| characters (Unicode code points) | 111 559 | 29 145 | 7 372 | 42 533 |
| lines | 2 356 | 567 | 160 | 388 |
| pages (`<!-- page N -->`, 1..N once each) | 71 | 15 | 6 | 16 |
| heading lines (`^#{1,6} +\S`) | 188 | 51 | 8 | 6 |
| body headings by level | 1:29 2:78 3:65 4:15 | 2:21 3:27 4:2 | 2:6 3:1 | 2:5 |
| `secLevel` (see §5) | 1 | 2 | 2 | 2 |
| sections / subsections | 29 / 78 | 21 / 27 | 6 / 1 | 5 / 0 |
| PART headings | 5 | 0 | 0 | 0 |
| tables (separator rows) | 20 | 5 | 7 | 0 |
| figure placeholders | 190 | 43 | 4 | 0 |
| … of which block-level | 186 | 35 | 4 | 0 |

Structural facts that drive the parser design — every one of these was checked against the
files, and several contradict the "idealised markdown" assumption:

1. **No code fences, no horizontal rules, no markdown links or images anywhere.** The only
   raw HTML is `<br>` (24 occurrences, all inside table cells) and the page-marker comments.
2. **Heading level semantics differ per document.** `#` is a chapter marker in the guide
   book (29 body occurrences) but appears exactly once — as the document title, *before*
   `<!-- page 1 -->` — in the other three. Any rule that hard-codes "H1 = chapter" is wrong.
3. **Ordered lists restart across pages.** Page 29 of the guide book begins with `3.`. The
   renderer must emit `<ol start="N">` using the literal first number, never auto-numbering.
4. **Ordered-list items carry indented child blocks** (3–4 spaces): paragraphs, figures,
   blockquotes and nested bullets (seen at indent 2, 3, 4 and 6).
5. **Blockquotes are the manuals' "Note / Warning / Prohibited / Required" callouts**
   (189 + 36 + 2 + 2 quoted lines) and contain paragraphs, lists *and* figures.
6. **Figure placeholders are usually block-level but sometimes inline** — 4 in the guide
   book (`the Pad *[pad icon]* tab`), 8 in the startup guide (`*[QR code]* CASIO Sampler
   App`). So placeholders are an **inline** node; a paragraph consisting of exactly one
   placeholder is promoted to a `<figure>`.
7. **`**[Example]**` exists** — strong emphasis must be matched before a placeholder, or a
   bold bracket is mis-lexed as a figure.
8. **`\*` escapes exist** (12 in midi, 4 in the guide book — footnote asterisks).
9. **Duplicate heading text is common** (`## ⚠ Warning` ×4, `# CREATIVE NOTE` ×3,
   `## Apache-2.0` ×2, three identical `# Automatically distribute …(continued)`), so
   anchor slugs must be de-duplicated per document.
10. **Tables can have an empty header row** (`| | |` in midi's product-information table)
    and cells contain `<br>`, inline code and bold.
11. **`oss.md` contains bare `http://…` URLs** in licence text. They are rendered as plain
    text. The M0 "no external origin" grep only covers `site/public/index.html` and
    `index.js`, so this is safe — but do **not** widen that grep to the whole output.
12. **Guide-book body pages carry a running header** — a whole-line-italic line among the
    first two non-blank lines of the page, e.g.
    `*Finger drumming along with a looped sound — PART 1: Part: Pad play*` (58 of 71 pages).
    On section-opening pages the `#` heading comes first and the running header second.
    The other three documents have none. This is the signal that makes §5's grouping exact.

## 4. Content model and parser strategy

### 4.1 Why compile-time embedding + runtime parsing

Three routes were considered:

* **JSON emitted by a preprocessing script, fetched at runtime.** Rejected: it needs a JSON
  decoder in the app (aeson's wasm dependency closure is ~15 packages — a build risk the
  milestone does not need), an async load path, and it splits the content logic across two
  languages.
* **Parse at compile time and `lift` the AST.** Rejected: lifting a parsed AST of 191 KB of
  markdown produces a very large literal expression; GHC compiles big literal data
  structures slowly and hungrily, and this machine has 3.9 GiB of usable RAM (M0 risk R4).
  Embedding raw text costs one string literal (P1) and no measurable compile time.
* **Embed raw text, parse lazily in Haskell at runtime.** Chosen. One language, zero new
  dependencies, no fetch, works offline and at any Pages sub-path, and the parsed model is
  available *synchronously* to the initial Miso model — which keeps the app a pure
  `Route -> View` function and makes browser assertions deterministic. Cost is +79 KB
  gzipped (P6) and a few milliseconds of parsing, bounded by laziness (§4.4).

### 4.2 Module layout

### 4.3 Types

```haskell
data Doc = Doc
  { docSlug     :: !Text          -- "guide-book"
  , docTitle    :: !Text          -- from the '# ' line before <!-- page 1 -->
  , docPreamble :: [Block]        -- the translator's note blockquote
  , docPages    :: [Page]         -- lazily parsed, in order, 1..N
  }

data Page = Page
  { pageNumber  :: !Int
  , pageHeader  :: Maybe Text     -- running header, verbatim, without the '*'s
  , pageBlocks  :: [Block]        -- LAZY: forced only when the page is viewed
  }

data Block
  = Heading   !Int [Inline] !Text          -- level, inlines, unique anchor slug
  | Para      [Inline]
  | Figure    !Text [Inline]               -- kind ("Figure"/"QR code"/…), caption
  | Bullets   [ListItem]
  | Numbered  !Int [ListItem]              -- literal start number
  | Quote     [Block]
  | Table     (Maybe [[Inline]]) [[[Inline]]]   -- header row (Nothing if blank), body
  | Unparsed  !Text                        -- MUST never occur; see §9

data ListItem = ListItem { liContent :: [Inline], liChildren :: [Block] }

data Inline
  = Str      !Text
  | Strong   [Inline]
  | Em       [Inline]
  | Code     !Text                         -- `…`
  | Break                                  -- <br>
  | Placeholder !Text !Text                -- kind, full text of *[…]*
  | PageRef  !Int !Text                    -- cross-reference, display text
```

### 4.4 Laziness contract

`Doc` is built by splitting the embedded `Text` on page markers — one linear pass — and
`pageBlocks` is a thunk. Viewing one page forces the block parser for that page only.
The stats blob (§9.1) and the outline force the *line-level* scan of all four documents
(~191 KB, single pass, no block parsing). Do not add strictness annotations to
`pageBlocks`, and do not `deepseq` the corpus at boot.

### 4.5 Block grammar (line-oriented, indentation-aware — not CommonMark)

Applied to the lines of a single page, after the page marker is removed.

| Rule | Pattern | Produces |
|---|---|---|
| blank | `^\s*$` | block separator |
| heading | `^(#{1,6}) +(.*\S)\s*$` | `Heading level (inline caption) anchor` |
| running header | whole-line italic `^\*([^*].*[^*])\*$` among the **first two non-blank lines** of the page, and not itself a placeholder | `pageHeader`; consumed, not a block |
| table | one or more consecutive `^\s*\|` lines; a `^\s*\|[\s:\|-]+\|\s*$` row separates header from body | `Table` |
| blockquote | consecutive `^\s*>\s?` lines; strip the marker and **recursively parse the remainder as blocks** | `Quote` |
| ordered item | `^(\s*)(\d+)[.)]\s+(.*)$` | starts/continues a `Numbered`; the first item's number is the `start` |
| bullet item | `^(\s*)[-*+]\s+(.*)$` | starts/continues a `Bullets`; nest by indent width |
| list child | a line indented **≥ 2 spaces more than the current item's marker**, or an indented block after a blank line inside a list | appended to `liChildren` by recursive block parse |
| paragraph | anything else; consecutive lines join with a space | `Para` |
| fallback | a line no rule consumes | `Unparsed` — **must be zero corpus-wide** |

Notes: lists are separated from a following paragraph by a blank line *and* a return to
column 0. Table rows are split on `|`; leading/trailing empty cells from the outer pipes are
dropped; a header row whose cells are all blank yields `Nothing`.

### 4.6 Inline grammar

Scanned left to right; **longest/most-specific marker first**:

1. `\` + any char → literal char (`\*` → `*`).
2. `` `code` `` → `Code`.
3. `**…**` → `Strong` (checked before `*`, so `**[Example]**` is bold, not a placeholder).
4. `*[…]*` on one line → `Placeholder kind text`, where `kind` is the text up to the first
   `:` or `]` (e.g. `Figure`, `Photo`, `Screenshot`, `QR code`, `Barcode`, `pad icon`).
5. `*…*` → `Em`.
6. `<br>` (case-insensitive, optional `/`) → `Break`.
7. `p. N`, `p.N`, `pp. N-M`, `pp. N–M` → `PageRef` **only when `1 ≤ N ≤ docPages`**;
   otherwise plain text. This is what makes the guide book's Index and its ~40 internal
   cross-references navigable, and it is the shape M2 will reuse to cite pages.
8. Anything else accumulates into `Str`.

A `Para` whose inline list is exactly one `Placeholder` is promoted to a `Figure` block.

### 4.7 Anchors

`slugify` = strip inline markers → lowercase → replace runs of non-`isAlphaNum` with `-` →
trim `-` → empty becomes `section`. `isAlphaNum` is Unicode-aware, so the Index's
`### あ row` keeps its kana. Duplicates within a document get `-2`, `-3`, … in document
order. Rendered as `id="h-<slug>"` on the heading element; pages render `id="page-<n>"`.

## 5. Navigation design

### 5.1 The rule

Uniform across all four documents, entirely derived from the text:

1. **`secLevel`** = the smallest heading level occurring **at least twice** in the body
   (everything after the `<!-- page 1 -->` marker). → guide-book 1, others 2.
2. **Sections** = headings at `secLevel`. **Subsections** = headings at `secLevel + 1`,
   attached to the preceding section. A section spans from its page to the page before the
   next section's page.
3. **Parts** = sections whose text matches `^PART\s+\d+\b`. If fewer than two exist, the
   document has a single flat, ungrouped section list and step 4 is skipped.
4. **Groups**, when parts exist:
   * `Front matter` — sections before the first part (title supplied by the UI, not the
     document; it is a UI label, not manual content).
   * one group per part, titled with the **part heading's own text verbatim**
     (`PART 1 — Part: Pad play`), running to the next part.
   * `Appendix & reference` — begins at the **back-matter boundary**: the first section
     after the last part for which **no page in that section's page span carries a running
     header naming a part** (`PART\s+\d+`). The last part's group ends there. If no such
     section exists, the last part simply runs to the end of the document.

Rationale for step 4's boundary: the guide book's `# Appendix` divider page (p. 62) carries
no running header, while every page of PART 4 (pp. 46–61) does. That is a real, textual
signal — it does not require knowing the word "Appendix".

### 5.2 Golden outline (the acceptance target)

`exe:content-check` must reproduce this exactly.

**guide-book** — secLevel 1, 29 sections, 78 subsections, 7 groups:

| Group | Pages | Sections |
|---|---|---|
| Front matter | 1–11 | 5 — p1 *Portable Standalone Sampler SXC-1 Guide Book (User's Guide)*, p3 *Safety precautions*, p7 *Operating precautions*, p10 *Names of parts*, p11 *Operation overview* |
| `PART 0 — Part: Preparation` | 12–13 | 1 |
| `PART 1 — Part: Pad play` | 14–26 | 3 — p14 part title, p15 *Finger drumming along with a looped sound*, p26 *CREATIVE NOTE* |
| `PART 2 — Part: Sampling` | 27–34 | 1 |
| `PART 3 — Part: Sequencer` | 35–45 | 2 — p35 part title, p45 *CREATIVE NOTE* |
| `PART 4 — Part: Leveling up` | 46–61 | 12 — part title, *Try layering pad performance over sequence playback* (47) … *CREATIVE NOTE* (61) |
| Appendix & reference | 62–71 | 5 — p62 *Appendix*, p63 *Troubleshooting*, p66 *Product specifications*, p67 *Reference information*, p69 *Index* |

**startup-guide** — secLevel 2, 21 sections, 27 subsections, ungrouped.
**midi** — secLevel 2, 6 sections (`1. Overview` … `Revision history`), 1 subsection.
**oss** — secLevel 2, 5 sections (`Apache-2.0` ×2, `BSD-3-Clause`, `MIT`,
`MICROSOFT AZURE RTOS`) — note the duplicate title, which exercises anchor de-duplication.

### 5.3 Glossary conformance

`translations/glossary.md` is embedded too, and `content-check` asserts that each of the
five binding chapter names — `Part: Preparation`, `Part: Pad play`, `Part: Sampling`,
`Part: Sequencer`, `Part: Leveling up` — appears in the glossary **and** as a substring of
exactly one guide-book part-group title. This mechanises the brief's "UI labels and
navigation must use these exact names".

### 5.4 Screens

* **Home** (`#/`) — project blurb, the disclaimer, and four manual cards showing title,
  page count and section count.
* **Manual contents** (`#/m/<slug>`) — grouped outline; each section links to its page,
  subsections listed beneath, page numbers shown on the right.
* **Page** (`#/m/<slug>/p/<n>`) — sticky header with breadcrumb (manual → group → section)
  and "Page n of N"; the rendered blocks; prev/next page links; the JA toggle; the

## 6. Routing design

**Hash routing, not pushState.** Reasons, in order of weight:

1. GitHub Pages serves static files only. A pushState path like `/repo/m/guide-book/p/17`
   404s on reload or on a shared link unless a `404.html` copy of `index.html` is shipped —
   a workaround that also breaks the "the artifact is a plain static directory" claim
   `check-site.sh` currently proves.
2. **The repo name is still unknown** (PLAN open question 1), so the Pages sub-path is
   unknown. Hash routes are sub-path-independent by construction.
3. All asset URLs stay relative to the same document base, so
   `pages/guide-book/page-17.webp` resolves correctly at any hosting depth (verified in P5).
4. `Miso.Router` is path-oriented (`popstate`, `pushState`, its own URI lexer). Feeding it
   hash strings means trusting its lexer with `/`-containing fragments. A hand-written
   parser is 40 lines, is a pure function of `Text`, and is **unit-testable in
   `content-check` without a browser** — which is worth more here than reusing a library.

```haskell
data Route
  = RHome                             -- "#/"
  | RManual !Text                     -- "#/m/guide-book"
  | RPage   !Text !Int !Bool          -- "#/m/guide-book/p/17"  (+ "/ja")
  | RNotFound !Text
```

`parseRoute` splits on `/` after dropping a leading `#`, ignores empty segments, and is
total. `renderRoute . parseRoute` round-trips for every constructor (asserted). Navigation
is by ordinary `<a href="#/…">` — the browser updates the hash, `windowSub "hashchange"`
fires, `update` re-reads `window.location.hash` via the Miso DSL (P4) and re-parses. That
gives working back/forward, middle-click, right-click-open-in-new-tab and shareable deep
links for free, with no `preventDefault` anywhere.

The initial route is read in `main` before `startApp`, so the first render is already the
requested page.

Unknown slug or out-of-range page renders a visible "not found" panel with a link home —
never a blank screen. Route-driven scroll: on every route change, `scrollIntoView "app"`.

## 7. Page-image delivery — decision and numbers

**Decision: commit WebP renders under `site/static/pages/<slug>/page-NN.webp`.**

Measured on the real PDFs (108 pages; `pdftoppm -r 150` output is 875×1241 for the three
A5 documents and 1241×1755 for midi):

| Format | guide-book | startup-guide | midi | oss | **total** |
|---|---:|---:|---:|---:|---:|
| PNG 150 dpi (today, gitignored) | 27.4 MB | 3.3 MB | 0.8 MB | 3.9 MB | **34.4 MB** |
| JPEG q82 (`pdftoppm -jpeg`) | 12.75 MB | — | — | — | ~16 MB |
| WebP q78 | 6.25 | 1.06 | 0.30 | 1.94 | **9.54 MB** |
| WebP q88 | 8.16 | 1.31 | 0.35 | 2.36 | **12.18 MB** |
| WebP lossless | 16.08 | 1.01 | 0.22 | 1.00 | **18.31 MB** |
| **per-page `min(q88, lossless)`** | ≈8.16 | ≈1.01 | ≈0.22 | ≈1.00 | **≈10.4 MB** |

The per-page minimum is the chosen encoding: it is self-tuning (lossless wins on the
text-only documents, lossy on the photo-heavy guide book), needs no per-document magic
constant, and gives byte-exact originals for the three documents where a reader is squinting
at Japanese licence and reference text. A side-by-side crop of guide-book p. 17 at 100 %
showed q78, q88 and the source PNG to be visually indistinguishable, so quality is not the
binding constraint; format choice is.

**Why commit rather than render in CI:**

* A fresh clone → `./scripts/build-site.sh` produces a *complete* site. Rendering at build
  time would add poppler + an image encoder to M0's prerequisite list, and M0's whole
  premise is that nothing is installed outside `~/.ghc-wasm`.
* CI stays unchanged: no `apt-get`, no ~35 s of rendering per run, no poppler-version drift
  between runners. The bytes reviewed are the bytes served.
* Cost is proportionate: the repo already carries a 75 MB PDF; +10.4 MB is +13 %, taking the
  clone to ~87 MB — still under GitHub's 100 MB advisory. The Pages artifact becomes ~13 MB
  against a 1 GB limit. Per-page transfer is ≤ 166 KB and only fetched when the reader
  actually opens the original, because the `<img>` is `loading="lazy"` and lives in a panel
  that is not rendered until toggled.
* The files are derived but *immutable* — the PDFs will never change — so they never churn
  in git history.

`scripts/render-page-images.sh` (new, committed, **not** part of the build) regenerates them
from the committed PDFs via `pdftoppm -r 150` into the already-gitignored
`manuals/pages/`, then encodes with `cwebp` if present, else Python 3 + Pillow (9.0.1 is
installed system-wide here). It is idempotent and prints a per-document size table.

**Presentation.** The JA panel is a `<figure id="ja-panel">` containing
`<img id="ja-image" loading="lazy" decoding="async">` wrapped in a link to the full-size
file (a zero-JS zoom escape hatch). At ≥ 60 rem the page view becomes two columns
(translation | original); below that the panel stacks under the translation, and a
"show original instead" behaviour is achieved by the panel being full-width — the CSS
decides beside-vs-instead, not the Haskell.

## 8. DOM and CSS contract

Fixed here so the CSS (wave 1), the app (wave 2) and both checkers (waves 2–3) can be built
against the same hooks. It is reproduced verbatim in every manifest prompt.


Block-level classes emitted by the renderer: `figure.md-figure > figcaption`,
`blockquote.md-note`, `div.table-wrap > table`, `span.md-placeholder`, `ol[start="N"]`,
`code`, `a.page-ref`. Headings inside a page carry `id="h-<slug>"`.

origin. Element **ids**, not `data-*`, for the same reason M0 chose them: Miso's `data_`
helper routes through `textProp`, whereas `id` is a real DOM property on both code paths.

markup survives beside it**, so `index.html` keeps only `#boot-status`, `<noscript>` and the
module script, and M0's static `<footer>` is removed to avoid a duplicate footer.

## 9. Verification design

M0's harness stays green in shape: `build-site.sh` → `check-site.sh` → headless Chrome via
`browser-check.mjs`, with the same boot contract (`window.__SXC1_BOOTED`,
`window.__SXC1_BOOT_ERROR`, `#boot-status`). The counter and its four ids are gone; the
assertions that referenced them are **replaced**, not deleted.

### 8.1 Three independent implementations must agree

The heart of the M1 harness is that the same numbers are computed three ways:

1. **`exe:content-check`** — the real Haskell parser, over the TH-embedded corpus, printing
   a stats JSON to stdout.
2. **`check-site.sh`** — a Python one-liner re-deriving the same numbers straight from
   `translations/*.md` with regexes, and diffing them against (1).
3. **the running app** — `#sxc1-content-stats`, a `<div hidden>` whose `textContent` is the
   same JSON, asserted by `browser-check.mjs` against the numbers `check-site.sh` passes it
   with `--expect-json`.

(1) vs (2) catches parser drift with a genuinely independent implementation. (2) vs (3)
catches a **stale build** — if someone edits a translation and forgets to rebuild, the
`chars` field diverges and the check fails loudly instead of silently serving old content.
That is the mechanical guarantee behind the brief's constraint 1.

Stats JSON, per document: `slug, title, chars, lines, pages, headings, figures, tables,
sections, subsections, parts, unparsed`, plus `partTitles` for the guide book. Every field
is computable by both a regex sweep and the parsed model. `chars` is `Data.Text.length` of
the embedded source = Python `len(open(f, encoding='utf-8').read())` (verified equal in P5:
111 559 / 29 145 / 7 372 / 42 533).

### 8.2 `exe:content-check` assertions

* page markers are `1..N`, each exactly once, in ascending order, for all four documents;
* **`Unparsed` count is 0 corpus-wide** — the strongest single parser check: the fallback
  rule exists precisely so it can be asserted empty;
* the golden stats table of §3 and the golden outline of §5.2 reproduce exactly;
* the five glossary chapter names map 1:1 onto guide-book part titles (§5.3);
* anchor slugs are unique within each document, and non-empty;
* `renderRoute`/`parseRoute` round-trip for a table of routes, and `parseRoute` is total on
  a table of malformed inputs (`""`, `"#"`, `"#/m"`, `"#/m//p/x"`, `"#/m/x/p/-1"`,
  `"#/m/x/p/9999"`, `"#/../../etc"`).
* exit non-zero with a readable diff on any failure.

### 8.3 `browser-check.mjs` assertions

1. boots; `#boot-status` hidden; zero console errors and zero uncaught exceptions
   throughout the whole run.
2. `#sxc1-content-stats` parses as JSON and matches `--expect-json` (or its built-in golden
   copy when the flag is absent).
3. `#/m/guide-book` renders a TOC containing all five exact strings
   `PART 0 — Part: Preparation` … `PART 4 — Part: Leveling up`.
4. `#/m/guide-book/p/17` renders `#page-17`, and its text contains
   `Tap the pads to make sounds`.
5. **JA toggle**: click `#btn-ja-toggle` → `#ja-image` exists, its `src` ends
   `pages/guide-book/page-17.webp`, and `img.complete && img.naturalWidth > 0` — i.e. the
   image really loaded, not merely that a tag was emitted. Click again → panel gone.
6. `#/m/guide-book/p/17/ja` deep-links straight into the JA-visible state.
7. prev/next: `#btn-next-page` moves the hash to page 18 and the content changes; prev
   returns; page 1's prev and page N's next are absent or disabled.
8. **cross-reference links**: guide-book p. 15 contains an anchor whose href is
   `#/m/guide-book/p/17` (the `p. 17` reference), proving §4.6 rule 7.
9. **every page of all four documents** (108 routes) renders a non-empty `#sxc1-page`, with
   no console error — this is M1's definition of done, mechanised. `--quick` limits it to a
   sample for fast iteration; the default is exhaustive.
10. **mobile**: with device metrics emulated at 390×844, on guide-book p. 10 (13-row table)
    and midi p. 3 (5-column implementation chart),
    `document.documentElement.scrollWidth <= window.innerWidth + 1` — no horizontal page
    scroll. Tables scroll inside their own `.table-wrap`.
11. `#sxc1-disclaimer` is present on a manual page and contains both
    `not affiliated` and `CASIO COMPUTER CO., LTD.`.

### 8.4 Negative controls (each must be demonstrated, not asserted in prose)

* corrupt one committed `.webp` → `check-site.sh` fails;
* run `browser-check.mjs --expect-json` with a deliberately wrong page count → fails;
* introduce a line the block grammar cannot classify in a scratch copy → `content-check`
  reports a non-zero `Unparsed` count;
* the M0 control still applies: garbage `app.wasm` → `check-site.sh` fails.

## 10. Risks

**R1 — cabal's `[relative-path-outside]` warning.** `extra-source-files: ../translations/*.md`
is required for rebuild correctness (P2) and produces one warning per component configure.
Accepted and documented; the alternative (copying the translations into `site/content/`
before every build) makes a bare `wasm32-wasi-cabal build` fail on a fresh clone.

**R2 — stale builds.** Mitigated structurally by §9.1's three-way stats comparison, which
turns silent staleness into a red check.

**R3 — the guide book's grouping rule is partly guide-book-shaped.** The `^PART \d+` and
running-header rules only fire on documents that have them; the other three degrade to a
flat section list. The rule reads *document text*, never a hard-coded chapter name — an
acceptance check greps the Haskell sources for the five chapter titles and must find none.

**R4 — parse cost on a phone.** Bounded by laziness (§4.4): a page view forces one page's
blocks. If it ever measures badly, the escape hatch is to memoise `docPages` per document
in the model; no interface change.

**R5 — `wasm-run.mjs` requires `~/.ghc-wasm/env`.** `check-site.sh` must source it (as
`build-site.sh` already does) and fail with an actionable message if absent, rather than
silently skipping the content check. `wasmtime run --dir=/` is the documented fallback.

**R6 — image weight in the repo.** +10.4 MB, one-time, immutable, regenerable. If the owner
later objects, the escape hatch is to move `site/static/pages/` to a CI render step; only
`render-page-images.sh` and one `build-site.sh` copy line would change, because the app
already refers to images purely by relative path.

**R7 — 108-route browser sweep runtime.** ~1–2 minutes in CI. Acceptable; `--quick` exists
for local iteration and the sweep reuses one browser session and one page target.

## 11. Task manifest — waves

`briefs/M1-manifest.json`, 6 tasks, disjoint `owned_paths`. Per the M0 lesson, every file a
task's `verify_commands` or prompt touches is inside its own `owned_paths`, produced by its
`depends_on` closure, or already committed by M0 — stated explicitly in each prompt.

| Wave | Task | Owns | depends_on |
|---|---|---|---|
| 1 | `page-images` | `scripts/render-page-images.sh`, `site/static/pages/` | — |
| 1 | `content-core` | `site/sxc1-trainer.cabal`, `site/src/`, `site/test/` | — |
| 1 | `reader-styles` | `site/static/index.html` | — |
| 2 | `reader-ui` | `site/app/`, `scripts/browser-check.mjs` | page-images, content-core, reader-styles |
| 3 | `verification` | `scripts/check-site.sh`, `scripts/build-site.sh` | reader-ui, content-core, page-images |
| 4 | `docs-and-ci` | `README.md`, `.github/workflows/site.yml` | verification, reader-ui |

Notes on the shape:

* **`site/static/` is deliberately not owned as a directory.** `page-images` owns
  `site/static/pages/`; `reader-styles` owns `site/static/index.html`;
  `site/static/index.js` and `site/static/vendor/` are M0 files nobody touches.
* **`content-core` owns the cabal file** and declares all three components up front,
  including `exe:app`'s new `other-modules` and its `sxc1-trainer` library dependency. It therefore
  **cannot build `exe:app`** — its `View.*` modules arrive in wave 2 — and its
  `verify_commands` build only `lib:sxc1-trainer` and `exe:content-check`. `build-site.sh`
  is expected to be red between wave 1 and wave 2; that is stated in the prompt so nobody
  "fixes" it by inventing stub modules.
* **`reader-ui` owns `browser-check.mjs`** for the same reason M0 kept cabal + `Main.hs` +
  `build-site.sh` in one task: the app's DOM hooks and the driver that asserts them are one
  contract and one debugging loop. Splitting them would leave neither independently
  verifiable.
* **`verification` owns `build-site.sh`** only to add `exe:content-check` to the build, so
  that `check-site.sh` can keep M0's "checks never build" property.
* `docs-and-ci` is wave 4 rather than a wave-3 sibling precisely because it reads
  `scripts/check-site.sh` — this is the M0 `ci-workflow` race, removed by construction.
